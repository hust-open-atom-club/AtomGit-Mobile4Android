## 1. 技术目标

首版是单 Activity 的原生 Android 应用，直接调用已验证的 AtomGit OpenAPI，服务当前登录用户。

两条主链路：

1. **动态**：展示本人及选定项目的近期活动，能分页、刷新，并能跳到关联事项或项目。
2. **待办**：列出需要当前用户处理的 Issue / Pull Request，进入详情后评论或批准，回读服务端结果，再更新列表分类。

仓库文件和流水线为处理待办提供上下文，也可从「我的项目」「我的组织」进入。底部固定四个入口：**动态、待办、通知、我的**。登录后默认进入动态。

| 数据 | Base URL |
| --- | --- |
| 用户、仓库、组织、Issue、PR、评论、文件、动态、通知 | `https://api.atomgit.com/api/v5` |
| Actions 流水线 | `https://api.atomgit.com/api/v8` |

`/api/v5` 与 `/api/v8` 是两套并存的接口前缀，不是同一个 API 的新旧版本。v8 的流水线路径打到 v5 上会 404。认证头统一为 `Authorization: Bearer <token>`。每个端点的路径、分页、权限和字段以实测为准。

首版认证只用 PAT。OAuth 若依赖不能放进 APK 的 `client_secret`，或需要单独的推送服务，就另立服务端方案，不计入本期工时。

## 2. 技术范围

### 2.1 必选

| 模块 | 技术交付 |
| --- | --- |
| 动态 | 本人与选定项目事件、来源与时间、分页、下拉刷新、关联跳转、部分失败 |
| 待办 | 待处理与我发起分源查询、各自分页、已验证筛选、详情入口、写后回读并刷新分类 |
| 通知 | 选定项目范围内拉取、未读、跳转、按所选 ID 批量标已读并报告部分失败 |
| 会话 | 单账号 PAT、有效性检查、资料、设置、退出与撤销指引 |
| 项目与组织 | 我的项目及范围内检索、我的组织、组织下可访问项目；README、分支、标签、懒加载文件树、提交列表 |
| Issue | 列表与详情、评论读取与发表、基础状态筛选 |
| PR | 列表与详情、按文件加载基础 diff、普通评论、正式批准、状态展示 |
| CI | 项目级 v8 运行列表与状态，加网页入口。PR 关联运行只在关联规则验证通过后启用 |
| 体验 | 手机布局、深色模式、加载 / 空 / 错误 / 重试、四入口与详情的状态恢复 |

待办查询以验证记录为准。候选条件：

- Issue：`created` / `assigned` / `all`
- PR：`created_by_me` / `assigned_to_me` / `need_my_approve` / `need_my_review`

待处理只包含：分配给我的未完成 Issue、待我批准的 PR、待我评审的 PR。`all` 的结果整体不是「待我处理」。「我创建的 Issue」「我发起的 PR」是跟进分类。没有完整计数接口时，界面显示已加载条数，或省略总数。

### 2.2 条件扩展

接口已验证、必选进度正常、且不占用第 11–12 周时，才单独立项。立项时补工时和验收标准。验证通过不等于自动变成必选。

更大范围的动态聚合与混合分页、更多待办类型、带快照的全部已读、OAuth 与多账号、项目统计、全局搜索、Star / Fork 写操作、Issue 新建 / 指派 / 状态修改、PR 行内评论与高级 diff、流水线日志和制品下载、折叠屏与平板布局。

### 2.3 本期不做

代码搜索、全站消息中心、正式 request-changes、AI 辅助、后台推送、组织管理、项目看板、推荐与全站发现、独立仓库 Tab、商店上架、配套服务端。

未验证的能力不放置入口。普通评论的成功状态只表示评论已发表。评论成功不改变 Issue 的完成分类，批准成功不表示 PR 已合并，通知已读不改变待办状态。

## 3. 总体架构

采用官方推荐的分层和单向数据流。首版一个 Gradle 模块，按功能和职责分包。出现明确的复用、隔离或构建边界时再拆模块。

```text
用户操作
  → 屏幕 ViewModel
  → Repository，或少量 UseCase
  → Remote（Retrofit）/ Local（Room、DataStore、Keystore）
  → 映射为领域模型
  → StateFlow
  → collectAsStateWithLifecycle()
```

| 层 | 职责 | 边界 |
| --- | --- | --- |
| UI | Compose 展示；把点击、输入交给 ViewModel 方法 | 不持有 Retrofit、DAO、Token |
| ViewModel | 屏幕状态的唯一对外出口；把操作转成一次用例调用 | 暴露只读 `StateFlow`；不解析 JSON |
| Domain | 仅跨屏幕复用或分支较多的逻辑，例如把多路待办查询收成「待处理 / 跟进」 | 不为单个 GET 包一层空 UseCase |
| Repository | 选择权威数据源，映射 DTO，执行缓存、去重、写后刷新 | UI 与 ViewModel 只依赖 Repository 接口 |
| Remote | v5 / v8、分页、错误、重试 | 返回 DTO 或已映射的错误，不返回界面文案 |
| Local | 摘要缓存、设置、凭据密文 | 详情类大对象默认不入库 |

依赖用 Hilt 构造函数注入。图片用 Coil。设置用 DataStore。序列化库在 kotlinx.serialization 与 Moshi 中选一个，全项目只留一种。

建议包划分（根包名在仓库立项时确定，下面是相对结构）：

```text
di/
navigation/
ui/
  theme/ components/
  feed/ todo/ notification/ profile/
  repo/ org/ issue/ pullrequest/ pipeline/ auth/
domain/          仅在出现复用逻辑时添加
data/
  remote/        v5、v8、DTO、拦截器、错误、分页
  local/         Room、DataStore、Keystore
  repository/
```

每个屏幕的状态用不可变数据类，至少包含：内容、加载、刷新、空、错误、部分失败。列表另含分页游标或下一页页码、是否还有下一页。写操作另含提交中与「尚待同步」。

## 4. 导航与状态恢复

单 Activity，一条主导航。第 2 周用一个最小原型固定方案，之后不混用两套栈：

1. 优先看 Navigation 3 的稳定版能否表达四个顶层入口、共享详情路由，以及返回后保留列表状态。
2. 依赖不合适或返回栈无法保留来源页状态时，采用 Navigation Compose，并在设计文档写下原因。

路由分成两类：

| 类型 | 页面 | 状态归属 |
| --- | --- | --- |
| 顶层 | 动态、待办、通知、我的 | 各自 ViewModel；切换 Tab 不销毁已加载的第一页，除非用户下拉刷新或写操作要求失效 |
| 详情 | Issue、PR、项目、组织 | 全入口共用同一路由。参数只有账号范围内的资源标识，不携带「来自哪个 Tab」的业务状态 |

从详情返回时，来源列表的筛选、分类和滚动位置仍在来源 ViewModel。旋转和进程重建要恢复的内容放进 `SavedStateHandle`：当前路由、动态来源、待办分类、项目或组织筛选、草稿文本。ViewModel 内存只覆盖进程还在的情况。跨进程要保留的设置放 DataStore。

登录门禁在导航图外层：本地没有可用会话时只显示登录；会话校验失败时清空凭据并回到登录。退出登录同时清会话、数据库、图片缓存和进行中的分页。

## 5. 会话与凭据

首版会话模型是单账号 PAT。

```text
用户粘贴 PAT
  → 先用它请求当前用户，确认 200
  → Keystore 中的 AES-GCM 密钥加密
  → 只把密文和账号标识写入应用存储
  → 进入动态
```

- 密钥放 Android Keystore，算法 AES-GCM。磁盘上不出现明文 Token。
- 备份规则排除凭据密文。Keystore 密钥失效时删除密文和本地缓存，要求重新登录，不用明文存储顶上。
- 不使用已弃用的 EncryptedSharedPreferences 作为实现方案。
- PAT 没有刷新。收到 401 就结束会话。
- 退出页面给出在网页端撤销 PAT 的说明。客户端删本地密文，撤销本身在服务端完成。
- 缓存、数据库、图片缓存和分页键从第一版就带账号标识。多账号仍是扩展；键上留账号是为了以后隔离，不是本期做切换。

OAuth 只在第 1–2 周做可行性记录：应用注册、授权域名、回调 URI、公共客户端、PKCE、`state`、scope、刷新是否可用。验证方式是系统浏览器或 Custom Tabs。`client_secret` 不进入 APK，也不复用其他应用的客户端凭据。记录结果供扩展评估，不进入首版验收。

## 6. 网络

两个 Retrofit 接口，两套 base URL，共用一个 OkHttp 客户端。

```text
OkHttp
  ├── 日志拦截器：脱敏，不打印 Authorization、PAT、Set-Cookie
  ├── 认证拦截器：仅当主机是已配置的 API 主机时附加 Bearer
  ├── v5 Retrofit
  └── v8 Retrofit
```

Markdown 里的图片、相对链接和用户点开的网页走不带 Token 的请求或系统浏览器。下载若发生重定向，重定向目标不是受信任 API 主机时去掉认证头。

错误映射成密封类型，界面只消费这一层：

| 类型 | 来源 | 界面行为 |
| --- | --- | --- |
| 未登录 | 401，或本地无会话 | 清凭据，回登录 |
| 无权限 | 403 | 独立空态，可去网页 |
| 不存在 | 404 | 说明资源删除或无法定位，可去网页 |
| 限流 | 429 | 按 `Retry-After` 等待；没有该头时指数退避加抖动，次数有上限 |
| 网络 | 超时、断网、取消 | 保留已有内容，提供重试 |
| 解析 | 2xx 但 DTO 对不上 | 记为该源失败，不用空列表伪装成功 |
| 部分失败 | 多个仓库或来源里只有一部分失败 | 展示成功部分，并标出失败来源 |
| 写入不确定 | 超时或无响应体 | 不自动再提交；先回读。回读也不能确认时显示尚待同步 |

只对明确的幂等读自动重试。评论、批准、标已读失败后由用户再次触发。

分页不设全局默认值。每个端点单独记录：页码还是游标、参数名、页大小、终止条件（空页、`Link`、总数或 `has_more`）、响应是数组还是对象。契约测试锁住方法、路径、查询参数和 DTO。

协程取消必须传到 OkHttp Call。响应体设置读取上限，超限按截断或失败处理，不把无限流读进内存。

## 7. 本地数据

权威数据在服务端。本地只保存会话、设置，以及重启后仍要立刻显示的摘要。

| 数据 | 存储 | 规则 |
| --- | --- | --- |
| PAT 密文、账号 id | Keystore + 排除备份的存储 | 退出和 401 时删除 |
| 主题等设置 | DataStore | 与账号无关的项和账号相关的项分开 |
| 仓库摘要、待办摘要 | Room | 主键含账号、资源类型、仓库、资源 id；有容量和过期时间 |
| 动态、通知的已加载页 | Room 或内存，第 2 周按数据量二选一 | 刷新时按去重键合并，不把多源第一页当成全量时间线 |
| 文件内容、diff、评论线程、流水线详情 | 不持久化 | 进入页面再请求 |

写成功后的刷新顺序固定：

1. 回读被修改的 Issue 或 PR。
2. 用回读结果更新详情。
3. 重新查询受影响的待办分类。
4. 只有分类查询结果变化后，才把事项移入、移出待处理或跟进。
5. 回读失败时详情保留原内容，并标记尚待同步。

动态浏览不写待办，也不写通知已读。通知已读只更新通知记录的已读字段。

## 8. 分模块方案

### 8.1 动态

数据源是已验证的「本人事件」和「选定项目事件」，两者分开持有分页状态。去重键用接口给出的事件 id；没有稳定 id 时用账号、来源、资源标识和时间。选定项目有数量上限，第 2 周写死。

展示按时间排序。若做混合时间线，必须先验证跨源继续加载时全局顺序仍然正确；做不到就按来源分栏或分段，并在界面标明。某一源失败时保留其他源，顶部或段内显示部分失败。

事件能解析到 Issue、PR 或项目时，跳到共用详情。解析失败时保留原文，并给出网页入口。通知接口和待办列表不接入这条流。

### 8.2 待办

每一类调用一个已验证的单条件接口，各自分页，不在客户端把各类第一页拼成「全部待办」。

界面两个分组：

- **待处理**：`assigned` 且未完成的 Issue；`need_my_approve`；`need_my_review`。实际参数名以验证记录为准。
- **跟进**：`created` 的 Issue；`created_by_me` 的 PR。

列表项的领域模型统一为：标题、仓库、类型（Issue 或 PR）、状态、更新时间、资源 id。去重键是账号 + 仓库 + 资源 id。筛选项只放验证过的状态和项目；若筛选只能发生在已加载数据上，控件标明「当前已加载结果」。

### 8.3 Issue 与 PR

Issue 详情加载正文和评论，提交普通评论。成功后把新评论并入详情，并走第 7 节的刷新顺序。评论 API 的 2xx 不解释成 Issue 已关闭。

PR 详情按文件请求 diff。领域模型区分新增、删除、重命名、二进制、截断。单次 diff 有第 2 周确定的大小上限，超过则该文件改为说明加网页入口。批准前再读一次 PR：状态或 head 与用户正在看的版本不一致时，先提示重新查看，不发批准。批准请求返回后回读。客户端检查不代替服务端权限。

演示和测试使用作者、评审者两个身份。只读身份用于确认 403 的展示。

行内评论在验证记录里分成三条：读取已有评论、回复、新建。只有新建的端点、文件、行号、提交版本和过期行为都验证通过，才允许作为扩展立项。读取或普通评论成功不作为新建已实现的证据。

### 8.4 通知

在选定项目集合内拉取与当前用户相关的通知。每个项目自己的分页和错误分开记录。并发数有上限。一个项目失败时，总状态是部分失败，不显示全部同步成功。

必选的已读是「当前选中的通知」：按仓库分组提交，逐条或逐批回读，失败项留在未读并说明。扩展里的全部已读必须先固定快照，收齐 ID 再分批提交，避免边翻页边修改造成漏项。

通知能定位到 Issue、PR 或项目时进原生详情。资源删除、无权限或无法定位时说明原因，并提供网页入口。仓库事件流不作为通知数据源。

### 8.5 我的、项目与组织

我的页面读取当前用户资料，并提供我的项目、我的组织、会话状态和设置。

- 我的项目：当前用户有权访问的仓库，分页；检索若不是服务端查询，标明范围。
- 我的组织：当前用户所属组织。空列表、403、请求失败三种状态分开。公共组织搜索结果不进入此列表。
- 组织详情：只列当前用户在该组织下可访问的项目。

项目详情是共用页，内含 README、分支、标签、文件树、提交、Issue / PR 入口、CI 入口。文件树按目录懒加载，路径和分支名按该接口要求编码。Markdown 渲染相对链接和图片时把它们解析到仓库内容地址，不执行脚本。大文件或无法预览的格式显示说明和网页入口。

### 8.6 CI

使用 v8 客户端读取项目的运行列表和状态。未知、无权限、没有运行记录分开展示。每条运行提供打开网页的入口。

PR 上的关联运行要有验证过的关联键（提交 SHA 或分支）。对不上时不显示仓库最新一次运行。日志和制品下载留在扩展：若做，必须流式读写、限制大小、可取消、失败可恢复，不以常驻前台服务作为默认方案。

## 9. 第 1–2 周要冻结的技术决定

这 24 人时的产出是一组会约束后续代码的记录，不是界面临时稿。每条能力一张表：网页上的动作、HTTP 方法与路径、权限差异、分页和排序、去重键、落到哪个页面、写后回读字段、结论（必选 / 扩展 / 不做）。

验证顺序按风险：

1. PAT 读取当前用户；同时记录 OAuth 条件。
2. 待办各类查询的筛选、排序、去重和有没有总数。
3. 专用测试仓库上的普通评论、正式批准和回读；记录作者、评审者、只读用户。
4. 本人事件与项目事件的类型、时间、去重、关联对象、分页上限。
5. 通知的项目范围、已读请求编码和回读。
6. 我的项目、我的组织、组织项目的权限和分页。
7. v8 运行列表；若要做 PR 关联，验证关联键。
8. 行内评论的读、回复、新建分开记录。

第 2 周末固定：

- 最低 SDK、目标 SDK、依赖版本和测试矩阵（最低版本、一个中间版本、目标版本，至少一台真机）
- 导航库
- 序列化库
- 动态聚合方式与选定项目上限
- 通知项目上限与刷新并发
- 列表、README、diff 的代表性数据量和降级阈值
- 只包含已验证必选能力的验收清单

必选接口不通时写明原因，由导师确认替代。替代方案未确认前，不用 Mock 数据宣布该功能完成。Mock 只用于自动化测试。

## 10. 实现顺序

依赖关系决定顺序：会话和网络在列表之前，写后回读在通知和项目浏览之前。测试随模块写。

| 阶段 | 时间 | 技术结果 |
| --- | --- | --- |

## 11. 测试与安全

| 层 | 做法 |
| --- | --- |
| 单元 | ViewModel 与 Repository。覆盖分页终止、错误映射、限流、取消、写入失败、待处理与跟进分类、无总数时的数量口径、评论或批准后的刷新、已读不改变事项状态 |
| UI | Fake Repository。覆盖默认进动态、刷新与跳转、四 Tab、通知定位、项目 / 组织进详情、写后回到列表、错误恢复 |
| 契约 | 本机 MockWebServer，走应用里的 OkHttp。断言方法、`/api/v5` 或 `/api/v8`、路径、参数、body 和 DTO。其他语言客户端的测试不算通过 |
| 真机 | 弱网、断网、401、403、重复点击、旋转、进程重建。业务仓库只读。评论、批准、标已读只打授权的测试仓库，并记录清理方式 |

安全检查：密文存储、备份排除、日志脱敏、HTTPS、外链不带 Token。OAuth 若后来纳入，再查 `state`、PKCE 和刷新失败。

CI 跑 assemble、静态检查、单元测试和一条 instrumentation。签名配置和 PAT 不进仓库。交付前在干净安装和一次覆盖安装上验证 Release APK。

## 12. 技术风险

| 风险 | 技术处理 |
| --- | --- |
| 待办筛选或总数字段与工作台不一致 | 以验证记录的查询条件为准；无总数则不显示总数；不用 `all` 充当待处理 |
| 没有稳定的人或项目事件接口 | 第 2 周改数据源和验收清单，动态不改用通知或待办填充 |
| 批准依赖 head 或第二身份 | 批准前强制重读；测试账号分成作者与评审者 |
| 通知按仓库拉取触发限流 | 冻结项目数、并发和刷新间隔；失败源单独标记 |
| PR 与流水线没有可靠关联键 | 只保留项目级运行列表 |
| Navigation 3 表达不了共享详情和返回恢复 | 第 2 周的最小原型失败则改用 Navigation Compose |
| 各接口分页形状不同 | 禁止全局 page size；每接口一份说明加契约测试 |
| 写请求超时但服务端已成功 | 不自动重试，先回读 |
| README 或 diff 过大 | 超过冻结阈值就降级到网页，避免主线程解析和 OOM |

进度落后时先停扩展，保留「登录 → 动态 → 待办 → 评论或批准 → 回读」。必选要删时同步改验收清单，经导师确认。
